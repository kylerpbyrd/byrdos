# Production Migration Runbook

This document provides the step-by-step procedure for applying Drizzle migrations in the byrdOS production environment. It inherits ADR-0000 §6 (Security-first development) and ADR-0010 (Deployment Pipeline and Migration Runbook).

## Scope

- Migrations live in `packages/db/drizzle/` and are generated by `drizzle-kit generate`.
- This runbook covers applying those migrations to the production Postgres instance.
- It assumes deployments follow the environment progression `local → preview → staging → prod`.

## Prerequisites

- Access to the production `DATABASE_URL` (stored in Fly.io / Render secrets or equivalent secret manager).
- `pg_dump` installed locally or in the deployment runner.
- `pnpm` installed and the monorepo checked out at the release commit.
- Network access from the runner to the managed Postgres instance (Neon / Supabase / RDS).
- A maintenance window or low-traffic period for migrations that add locks (e.g., `CREATE UNIQUE INDEX CONCURRENTLY` is preferred when supported).

## 1. Pre-migration checks

1. Verify the release commit in CI has passed lint, typecheck, tests, and build.
2. Confirm the migrations to be applied:
   ```bash
   pnpm --filter @byrdos/db db:migrate -- --dry-run
   ```
   Note: Drizzle Kit may not support `--dry-run` directly; if not, inspect the generated SQL files in `packages/db/drizzle/` before proceeding.
3. Check `drizzle_migrations` to identify the current applied state:
   ```sql
   SELECT id, hash, created_at FROM drizzle_migrations ORDER BY created_at DESC LIMIT 10;
   ```

## 2. Backup the production database

Take a full logical backup before any production migration. Store the backup in durable object storage with a retention label matching the release tag.

```bash
export RELEASE_TAG=$(git describe --tags --exact-match 2>/dev/null || git rev-parse --short HEAD)
pg_dump "$DATABASE_URL" \
  --no-owner \
  --no-acl \
  --clean \
  --if-exists \
  --file "byrdos-prod-backup-${RELEASE_TAG}.sql"
```

Validate the backup file size and run a spot-check restore query against a temporary Postgres instance before continuing.

## 3. Review the generated SQL

Read every `.sql` file that has not yet been applied. At minimum confirm:

- Each statement is intentional and matches the release PR description.
- New constraints use `CONCURRENTLY` where possible to avoid long table locks.
- No unexpected `DROP`, `TRUNCATE`, or destructive data-type changes are present.
- Column additions include sensible defaults or are nullable to keep old code paths working during rollout.

## 4. Destructive-change approval gate

Per ADR-0000 §6, destructive database changes require explicit human approval. A destructive change includes, but is not limited to:

- `DROP TABLE`, `DROP COLUMN`, `DROP INDEX`
- `TRUNCATE`
- Narrowing a column type in a way that loses precision or data
- Renaming a column or table without a backward-compatible alias or view

If any destructive statement is present:

1. Halt the automated deploy.
2. File a separate expand/contract plan (usually two migrations across two releases).
3. Obtain written approval from the Architect and the owning Backend or Security agent.
4. Only then proceed with the approved migration.

## 5. Apply the migrations

Run the migration command against the production database. This command executes `drizzle-kit migrate` from the `@byrdos/db` package context.

```bash
pnpm --filter @byrdos/db db:migrate
```

Ensure the environment variable `DATABASE_URL` points to production and that no other migration is running concurrently.

## 6. Verify migrations applied

After the command succeeds, confirm the new rows in the `drizzle_migrations` table:

```sql
SELECT id, hash, created_at
FROM drizzle_migrations
ORDER BY created_at DESC
LIMIT 10;
```

Cross-check the `hash` values against the `.sql` filenames in `packages/db/drizzle/` for the release commit.

## 7. Smoke test

Run a minimal set of checks before routing traffic:

1. `GET /health/ready` returns 200 and confirms Postgres + Redis connectivity.
2. Query one representative row from each affected table to verify schema semantics (e.g., a `UNIQUE` constraint does not already fail on existing data).
3. Trigger a non-production-affecting operation, such as a metrics scrape or a canary sync job, and confirm success.

## 8. Rollback guidance

### Application rollback

If the application misbehaves after migration but the schema is still compatible with the previous release:

1. Redeploy the previous application image.
2. Confirm `/health/ready` is healthy.
3. Monitor error rate and sync SLOs (see ADR-0012).

### Schema rollback

Down migrations are avoided in production. If a schema change is incorrect:

1. Restore from the pre-migration backup taken in step 2.
2. Alternatively, author a forward-fix migration that corrects the schema without data loss.
3. Never manually edit the `drizzle_migrations` table to hide a failed migration; always remediate transparently.

## 9. Concrete example: migration 0005

Migration `packages/db/drizzle/0005_heavy_sentinel.sql` adds three unique constraints:

```sql
CREATE UNIQUE INDEX "categories_user_norm_name_idx" ON "categories" USING btree ("user_id","norm_name");
CREATE UNIQUE INDEX "provider_connections_integration_external_id_idx" ON "provider_connections" USING btree ("integration_id","external_id");
CREATE UNIQUE INDEX "sessions_refresh_hash_idx" ON "sessions" USING btree ("refresh_hash");
```

This migration is non-destructive: it only adds unique indexes. It is safe to apply without the destructive-change approval gate, provided duplicate data has been remediated first. Before applying:

1. Run queries to detect duplicates:
   ```sql
   SELECT user_id, norm_name, COUNT(*) FROM categories GROUP BY user_id, norm_name HAVING COUNT(*) > 1;
   SELECT integration_id, external_id, COUNT(*) FROM provider_connections GROUP BY integration_id, external_id HAVING COUNT(*) > 1;
   SELECT refresh_hash, COUNT(*) FROM sessions GROUP BY refresh_hash HAVING COUNT(*) > 1;
   ```
2. Resolve any duplicates.
3. Apply the migration.
4. Verify the indexes exist in `pg_indexes`.

## 10. Post-migration

1. Update the deployment log / release notes with the applied migration IDs.
2. Monitor SLO dashboards (ADR-0012) for at least 30 minutes after migration.
3. Remove the backup file from the deployment runner after confirming it is stored in durable object storage.
